# OpenRAM SRAM Integration in Wildcat (Caravel Tapeout Project)

## Introduction

This project focuses on integrating a dense SRAM macro generated with OpenRAM into the Wildcat RISC-V processor, targeting a full ASIC flow using the Caravel framework and the Sky130 PDK.

The initial motivation was to replace the existing `SyncReadMem`-based memory used in the Wildcat design. While convenient at the RTL level, such memories are synthesized into flip-flops and multiplexers, leading to extremely inefficient area usage and unrealistic implementations for ASIC tapeout.

The goal is therefore to:
- Replace this memory with a compact SRAM macro generated by OpenRAM
- Integrate it into the Wildcat processor
- Harden the design using the LibreLane/OpenLane flow
- Prepare a design suitable for real tapeout

While the project initially appeared straightforward, integrating OpenRAM turned out to be one of the most challenging parts of the entire flow. Significant effort was required to handle memory generation, macro integration, and physical design constraints.

---

## Design

### Overview

The design consists of:
- The Wildcat RISC-V processor
- A custom SRAM block generated using OpenRAM
- Integration within the Caravel `user_project_wrapper`

The original memory inside Wildcat has been replaced by a dedicated SRAM macro.

---

### SRAM Architecture

- Current prototype: **256 × 32-bit SRAM**
- Generated using OpenRAM
- Intended to be replaced by a larger macro in the final version

The SRAM is integrated as a **hard macro (blackbox)**:
- The macro is generated externally (GDS + LEF + Liberty)
- The processor interacts with it through a defined memory interface
- The macro is instantiated at the top level during physical design

---

### Integration Strategy

The integration required several steps:

- Removal of `SyncReadMem` from the Wildcat design
- Adaptation of the memory interface to match SRAM behavior
- Instantiation of the SRAM macro in the design hierarchy
- Configuration of the OpenLane/LibreLane flow to support external macros
- Integration into the Caravel `user_project_wrapper`

---

### Practical Challenges

Although conceptually simple, the integration exposed several non-trivial issues:

- **OpenRAM generation complexity**  
  Generating a working SRAM macro required careful configuration and debugging.

- **LEF / GDS consistency**  
  Ensuring that the generated macro views (LEF, GDS, Liberty) were consistent and correctly interpreted by the flow.

- **DRC violations**  
  The generated memory introduced design rule violations that required investigation and mitigation.

- **Macro integration in OpenLane**  
  Hard macro integration is significantly more complex than standard-cell flows, requiring:
  - Correct placement constraints
  - Proper abstraction handling
  - Flow configuration adjustments

- **Flow instability**  
  Some stages of the flow (especially Magic and extraction) were sensitive to the macro and required iterative debugging.

Overall, integrating OpenRAM proved to be the **main bottleneck of the project**, both in terms of time and complexity.

## Design Implementation

The integration of the OpenRAM SRAM required modifications across multiple parts of the design, including RTL, memory abstraction, and physical configuration.

### OpenRAM Macro Files

The SRAM macro generated with OpenRAM includes the following views:

- `.v` — behavioral model of the SRAM
- `.lef` — abstract physical layout for place & route
- `.lib` — timing model for static timing analysis
- `.gds` — final physical layout

These files are required for proper integration into the ASIC flow and are referenced in the OpenLane configuration.

---

### Modified Files

#### `CpuTop.scala`

The original Wildcat design used a `SyncReadMem` for data memory, which is not suitable for ASIC implementation.

This file was modified to:
- Remove the `SyncReadMem`-based memory
- Interface the CPU with an external SRAM macro
- Adapt control signals for read/write operations

This modification is central to enabling a physically realizable memory.

---

#### `config.json`

The OpenLane configuration was updated to support the SRAM macro:

- Inclusion of SRAM `.lef`, `.gds`, and `.lib` files
- Configuration for hard macro integration
- Adjustment of flow parameters for macro handling

---

### Created Files

#### OpenRAM BlackBox

- `OpenRam256x32BlackBox.scala`

This file:
- Defines the interface between the CPU and the SRAM
- Allows synthesis without exposing internal SRAM implementation
- Matches the generated OpenRAM macro interface

---

#### SRAM Integration Module

- `OpenRamScratchPadMem.scala`

This module:
- Replaces the original `ScratchPadMem.scala`
- Connects the CPU to the OpenRAM SRAM
- Implements memory access logic compatible with the macro

---

### Existing Memory (Replaced)

- `ScratchPadMem.scala`

This file contained the original memory implementation based on `SyncReadMem`, which:
- Is suitable for FPGA
- Is not suitable for ASIC (mapped to flip-flops and multiplexers)

It was replaced by the OpenRAM-based memory module.

---

### Summary of Changes

The following transformations were performed:

- `SyncReadMem` → OpenRAM SRAM macro
- Internal behavioral memory → External hard macro
- FPGA-oriented design → ASIC-compatible implementation

This required coordinated changes across:
- RTL (Chisel modules)
- Memory abstraction
- OpenLane configuration
- Physical macro integration

## Final Remarks

This project highlights an important reality of ASIC design:

> Integrating a memory macro is not a trivial task, even when using open-source tools.

What initially seemed like a simple replacement of a memory block turned into a complex integration problem involving:
- Toolchain limitations
- Physical design constraints
- Non-trivial debugging across multiple abstraction levels

This experience provided valuable insight into the challenges of real-world chip design and tapeout preparation.
